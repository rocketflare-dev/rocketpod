# API Routes

Hono routers mounted in `src/api/index.ts`. Thin controllers: validate → authorise → query → respond.

## Layout

- `health.ts` — `/api/health`, `/api/ready`. Public.
- `auth/` — public (rate-limited where login-shaped): `session.ts` (`/auth/methods|session|select-tenant|logout` — logout answers `200 { endSessionUrl }` when an OIDC issuer advertises `end_session_endpoint`, else 204), `magic-link.ts` (`/auth/magic-link/request|verify`), `oauth.ts` (ONE generic `/auth/:provider` + `/callback` over `auth/providers` — incl. `oidc`; `?returnUrl=` (or `?redirectTo=`); under `AUTH_OIDC_ONLY` every other provider → `/login?error=oidc_only`; a Cognito `UserLambdaValidationException` at the token exchange → `/login?error=no_access`; under `OIDC_MANAGED_TENANCY` the callback runs `services/idp-tenancy.ts` `reconcileIdpClaims` before `completeLogin`), `dev-login.ts` (development only), `providers.ts` (linked identities), `cli.ts` (`/auth/cli?redirect_uri=&hostname=&state=` and `POST /auth/cli/confirm` — see *CLI login* below), `helpers.ts` (`completeLogin`, `safeRedirectPath`). Static routes mount BEFORE the generic `/:provider` router.
- `invite.ts` — public `GET /api/invite/:token`, cookie-required `POST /api/invite/:token/accept` (transactional).
- Behind `authMiddleware` (cookie or Bearer): `me.ts`, `tenant.ts` (current tenant + `/settings`), `tenants.ts` (mine; create — multi only), `members.ts`, `invitations.ts` (+ tenant-free `GET /pending`), `keys.ts`, `notifications.ts`, `activity.ts`, `access-requests.ts` (tenant-free), `files.ts` (`POST /api/files?scope=` multipart `file` → 201 `fileSchema`; `GET /:id` streams from `platform.storage` (S3-compatible) with `Cache-Control: private`, `ETag`/304, ONE HTTP `Range` (`parseByteRange` → 206 + `Content-Range`; ignored → 200; past the end → 416 `range_not_satisfiable`; `If-Range` on another ETag → the whole file), `inline` for `INLINE_MIME_TYPES` (the avatar images **plus `application/pdf`**) else `attachment`; a PDF sets `c.set('embeddable', true)` BEFORE the 304 return so the viewer can frame it (`../middleware/CLAUDE.md` row 4); ranges are served as in `../services/CLAUDE.md` § Streaming a stored object; `DELETE /:id` uploader-or-`delete File`; `avatars` scope writes `users.avatarUrl`; 503 `storage_not_configured` when `platform.storage` is null).
- AI, all behind `authMiddleware`; logic in `services/ai/*`, `services/agents/**`, `services/prompts.ts` — routes never import an SDK or read `ai_configs`:
  - `ai-config.ts` → `/api/ai/config`: `GET /` (rows as `aiConfigSchema`, `hasCredential` never the key; `read AiConfig`), `GET /providers` (the `PROVIDERS` catalog + `defaultMaxOutputTokens` — **no shared schema**, the UI parses it permissively), `GET /readiness` (`readiness()` — what the resolvers WOULD pick, no 503), `POST /test` (`testConfig` on a saved `configId` or an inline candidate; rate-limited 10/min/IP; `manage AiConfig`), `POST /` (upsert on `(tenant, scope, label)`; omitted `apiKey` keeps the stored one only while provider and normalised base URL match — otherwise 400 `api_key_required` (every provider needs a key); `isDefault` swaps inside one transaction, the first row in a scope is default; 201 create / 200 update), `DELETE /:id` (204). Every write is `services/ai/configs.ts`; the route only guards, records activity and answers.
  - `ai-prompts.ts` → `/api/ai/prompts`: `GET /`, `GET /:key` (member read), `PUT /:key` / `DELETE /:key` (`manage Prompt`; unknown key → 404 `prompt_not_found`; the registry is code).
  - `ai-usage.ts` → `GET /api/ai/usage/summary?from&to` (`summarizeUsage`, default 30 days, `from >= to` → 400 `invalid_range`; `manage AiConfig`).
  - `ai-agent-models.ts` → `/api/ai/agent-models`: `GET /` (every registry prompt key + assignment + the `effective` pick via `planChat` — the same function `resolveChat` uses), `PUT /:promptKey` (pin `aiConfigId` — tenant-scoped, foreign id → 404 `ai_config_not_found` — and/or `model`), `DELETE /:promptKey` (revert, idempotent 204); writes `manage AiConfig`.
  - `ai-documents.ts` → `/api/ai/documents`: `POST /ingest` (`ingestText` with `c.get('platform').jobs`; 201 with `status` `indexed` or `pending` when queued; `create Document`), `POST /upload` (multipart `file` + `title`/`source`/`visibility`/`groupIds` → `ingestFile` over `platform.storage` + `platform.jobs`; `uploadBodyLimit`, 413 `payload_too_large`, 415 `unsupported_media_type`, 503 `conversion_not_configured` for a type needing `platform.converter` when there is none), `GET /` (paginated, `?status=`), `POST /search` (`searchChunks` hybrid RRF), `GET /:id`, `GET /:id/content?offset=&maxChars=` (one character window over `documents.content`, sliced in Postgres; 409 `document_not_converted` / `document_conversion_failed` when there is no text), `GET /:id/passages` (paginated, columns named so `embedding` cannot leak), `GET /:id/card`, `DELETE /:id` (owner or `delete Document`; chunks cascade). All three reads go through `services/ai/document-content.ts`, the same service `get_document` uses. Vectors never leave the server, and the text only ever leaves one window at a time.
  - `chat.ts` → `/api/chat`: `GET|POST /conversations` (POST resolves the client FIRST → 503 `ai_not_configured` before any row; freezes `provider`/`model`), `GET|DELETE /conversations/:id`, `POST /conversations/:id/messages` — a thin wrapper over `services/ai/chat-turn.ts`: `prepareChatTurn` runs everything that can fail as JSON (resolve, `resolvePrompt('chat')`, last 40 turns, user-message insert), then `streamChatTurn` streams **AG-UI** (`RUN_STARTED → CUSTOM kit.chat.ids → STATE_SNAPSHOT → per-turn TEXT_MESSAGE_*/TOOL_CALL_* → CUSTOM kit.usage → RUN_FINISHED`, or `RUN_ERROR`; a cancelled run emits nothing). Frames are `data:` only — no `event:` line — or protobuf when the client negotiates it. Knowledge tools are on unless `CHAT_KNOWLEDGE_TOOLS=false`, built from the STREAM's client; writes inside the stream use **`streamDatabase(c)`** and are awaited, then `recordUsage`, then `tracer.flush()`. Ownership = `userId` filter on every query (others' threads 404, admins included).
  - `agui.ts` → `POST /api/agui/run`: the AG-UI `RunAgentInput` endpoint, mounted BESIDE `/api/chat` (the mount list is the enumerable auth surface). Validates `kitRunAgentInputSchema`, `update Conversation`, then reconciles — **the server is the transcript, the client supplies only the tail**: an unknown `threadId` is adopted as a conversation (after `resolveChat`, so a 503 precedes any row; one belonging to someone else → 404 `agui_thread_not_found`), the LAST message is the new user turn and earlier ones are ignored, a replayed UUID message id is not re-inserted, and `MESSAGES_SNAPSHOT` reports the server's transcript in-band. Non-empty `tools[]` → 400 `agui_client_tools_unsupported` (refused, never ignored). Then the SAME `streamChatTurn` the chat route calls.
  - `agents.ts` → `/api/agents`: `GET /` (registry); `GET /runs` (paginated, `?batchId=`; members their own, `isAdminLevel` all); `POST /runs` (`enqueueRun(db, cfg, c.get('platform'), …)` → 202 + row, `deduplicated: true` on an active exclusive run the caller may see, `?strict=1` → 409 `agent_run_active`; a run they may not see is always a bare 409; no `platform.runs` → 503 `agent_runs_not_configured`; 429 `agent_runs_limit` / `ai_budget_exceeded`); `POST /runs/batch` (`enqueueRunBatch`, ≤ 100 inputs of one NON-exclusive agent else 400 `agent_exclusive`; 202 with one item per input by `index` — an invalid input is an item error with no row, a failed engine create a `failed` row `workflow_create_failed`; one activity row per batch); `GET /runs/:id` and `GET /runs/:id/agui` (`requireRun` (lookup + the ownership 404) → read the log → `settleOnRead` (`reconcileRun` **and** `expireParkedRun`, the log's newest `at` as `lastEventAt`, so a live run costs **no** engine read) → the asks — the order is the contract; `interrupts[]` / `artifacts[]`, `GET /runs/:id` adds summed `usage`, `?events=0` is the bare row and reconciles unconditionally; `/agui` is plain JSON with `lastSeq` as the tail cursor; `loadRun` is both halves); `GET /runs/:id/agui/stream` (the LIVE tail, `services/agents/run-stream.ts`, GET so a bare `EventSource` works — rules in `../services/agents/CLAUDE.md`); `POST /runs/:id/cancel` (`requestCancel(…, realtime, c.get('platform'))` — cooperative, forced on a second cancel). `POST /runs/:id/interrupts/:interruptId` answers ONE ask: visible run → `canAnswer` (`update AgentRun` + the agent's `approvers` `'requester' | 'admin'`, 403) → the ask → `interruptPayloadSchema(spec)` — the SAME function the UI validated its draft with (400; an `editedInput` re-checked against the tool's stored schema) → `resolveInterrupt`'s single compare-and-set on `status = 'pending'` (null → 409 `interrupt_not_pending`: two people answering at once is one 200 and one 409, never a lost decision) → an `interrupt.resolved` row → **only when nothing is still pending**, `resumeRun` THEN `nudgeOrRestartInstance` (*the answer is the transition*). `POST /runs/:id/steering` appends a note through `appendEventAtomic` (409 on a settled run). `GET /interrupts?status=` is the tenant-wide inbox (own runs for a member, the tenant's for admin+, `canAnswer` PER ITEM rather than filtered). The route never runs the agent.
- `feedback.ts` (`/api/feedback`): thumbs on AI answers — `POST /` (`create Feedback`, every member; `services/feedback.ts` proves the rater can READ the target — own thread only, admins included; own run unless admin-level — and a foreign id is a 404), `DELETE /:target/:targetId` (withdraw your own vote, 204, idempotent), `GET /mine?target=&targetIds=a,b` (your own votes, for the thumbs' state), `GET /` (`read Feedback`, admin+ — the promotion queue, `?rating=up|down&target=`, paginated). A vote is also a zero-length `feedback` span under the answer's trace root.
- `evals.ts` (`/api/evals`): `GET /export?messageId=|runId=` → a draft `EvalCase` (question, earlier turns, retrieved passages, tools called, the observed answer as `expected.output`, the latest feedback) with `containsTenantData: true`. `read Feedback`, admin+; every lookup carries the tenant. The CLI's `evals promote` is the reader.
- `traces.ts` (`/api/traces`): the local AI trace store read back — `GET /` (one row per trace, `?runId|conversationId|since|agent|status`, paginated; status is the ROOT's once recorded, else "any span errored"), `GET /:id` (the trace's spans oldest first, parent-linked; `:id` is a trace id, an agent run id or an assistant message id, resolved in `services/traces.ts` with the tenant on every lookup, so another tenant's id is `404 trace_not_found` like an unknown one). `read Trace` — owner/admin/support only; spans hold other people's prompts, so a member cannot read even their own run's. The CLI's `traces list|show` is the reader.
- `guide.ts` (`/api/guide`, `docs/CONCEPTS.md` §18): the in-app Guide — `GET /toc` and `GET /page?path=` (the reader's own TOC; the audience is `guideAudienceFor(auth)`, so an admin page is the same 404 for a member as a missing one), `GET /images/:file` (bare filename, raster only), `POST /ask` (AG-UI on `resolveChat(..., { promptKey: 'guide-chat' })` with the ONE `search_guide` tool only this route builds, built on the STREAM's client; JSON 503 before the stream; ends with `CUSTOM kit.guide.answer`; stateless — usage row + trace only). Every member, session or API key; global static content through `platform.guide`, never the filesystem.
- `identity-events.ts` → `/api/identity/events`, mounted WITHOUT `authMiddleware`: the OIDC issuer's identity events under IdP-managed tenancy. The Standard Webhooks signature over the raw body (`auth/standard-webhooks.ts`, `IDENTITY_WEBHOOK_SECRET`) is the authentication; then `services/idp-tenancy.ts` `applyIdentityEvent`. 204 applied / stale / unknown person, org or type; 400 malformed known type; 401 bad signature; 404 not configured.
- `ws.ts` — `GET /ws?tenantId=`, mounted WITHOUT `authMiddleware` (a browser cannot set headers on an upgrade): resolves the cookie via `resolveCookieAuth`, checks membership in the requested tenant, then hands the identity to `c.get('platform').realtime.accept()` — the in-process hub (`src/node/realtime.ts`, fanned out across processes over LISTEN/NOTIFY; the upgrade completes in `src/node/server.ts`). Not an upgrade → 426 `upgrade_required`; no cookie → 401; not a member of `?tenantId` (or the session tenant) → 403; suspended → 403 `tenant_suspended`; no hub → 503 `realtime_not_configured`; else `hub.accept(request, { tenantId, userId, sessionId, globalAdmin, canRead })` — `canRead` is `realtimeTopicSubjects()` filtered by `buildAbility` for THIS membership's role (the session's features only when it is the session's tenant), the only input the hub's topic check reads. The hub trusts that identity **only** because this route is its sole caller — the server completes the handshake only when the route accepted (`src/node/server.ts`); never expose the hub another way.
- `groups.ts` (`/api/groups`): `GET /mine` (any member — their own groups); everything else is `manage Group` — `GET|POST /types`, `PATCH|DELETE /types/:id`, `GET|POST /`, `GET|PATCH|DELETE /:id`, `POST /:id/members { userIds }` (every id must already be a tenant member → 400 `not_a_member`), `DELETE /:id/members/:userId`. A delete that would change who can see content is 409 `group_in_use` with `{ documents, dashboards }` unless `?force=1`, and forcing narrows the affected resources (they keep `visibility: 'groups'` with fewer grants) — it never opens them. Membership changes nudge `entity.changed { entity: 'groups' }` tenant-wide AND `access.changed` to the affected users. `PUT /api/members/:userId/groups` is the same decision taken from the person's side.
- `features.ts` (`/api/features`): `GET /` — the EFFECTIVE flags for the active tenant, any member, answered from `auth.features` so it costs no query and cannot disagree with any other gate. It is what `rocketpod features list` reads, because a Bearer key cannot reach `/api/admin/*`. Administering flags is `admin.ts` (`GET /feature-flags`, `PATCH /feature-flags/:key`, `GET|PUT|DELETE /feature-flags/:key/overrides[/:tenantId]`) behind `globalAdminMiddleware`; `:key` is a registry key, NOT a uuid, so it is validated against `isFeatureName` and an unknown one is a 404. The override sub-routes call `requireMultiTenant` (with one organisation the platform state already IS its answer) and `PATCH` refuses a rollout counted in organisations there. An override change nudges `features.changed` to that tenant; a platform change does not — a fan-out to every tenant is one publish per tenant, so it lands on the next `GET /auth/session`.
- **Visibility** on every resource that carries it — core's `documents` plus each installed plugin's: `PUT /api/ai/documents/:id/visibility` is the document's OWNER or `manage Document`. Every read path ANDs the resource's predicate (`visibleDocuments(scope)`; a plugin's own comes from its `visibilityResources` entry) onto the tenant predicate, and answers the SAME 404 for a hidden row as for an absent one. `GET /api/files/:id` applies the OWNING DOCUMENT's visibility to a `documents`-scope object.
- Behind `globalAdminMiddleware`: `admin.ts` — the only cross-tenant surface; logic in `services/admin.ts`.
- An installed PLUGIN's routers live in `src/plugins/<id>/api/` and reach the mount table through
  `ServerPlugin.mounts` (spread in last, `/api/<id>`); the rules below apply to them unchanged
  (`../../plugins/CLAUDE.md`).
- Guard list, per mount: public — `health`, `/auth/*`, `GET /api/invite/:token`, and every installed plugin's `publicMounts` under `/api/hooks/<plugin id>` (consent callbacks and webhooks; the handler proves the caller — `verifyState`, a stored secret, a provider signature — before it touches a row, and the config test refuses a public mount anywhere else); `globalAdminMiddleware` — `/api/admin/*`; cookie-resolved — `/ws`; `authMiddleware` — every other `/api/*` and every prefix an installed plugin mounts (e.g. the analytics plugin's `/api/analytics`, `/cubejs-api` and `/mcp`, when installed — none is by default; the last two are ONE router mounted twice, because drizzle-cube registers absolute paths). A plugin's own guards are its business and use the same `guardPermission` over its own subjects.
- Logic lives in `services/{auth,tenants,members,invitations,admin,notifications,activity,email,jobs,realtime,storage,prompts}.ts`, `services/ai/*` and `services/agents/**`; routes validate → authorise → call a service → respond. `utils/db/tenant-helpers.ts` `onTenantCreated` is the post-commit tenant hook — core contributes none, so it is every installed plugin's hook, each best-effort in its own try/catch and handed the deployment's `features` (a hook that CREATES rows is the sharpest feature door there is). The one service per platform capability (`jobs`, `realtime`, `runs`, and `ai/resolve.ts` for `ai_configs` / `agent_models`) is listed in `../services/CLAUDE.md`.

## Rules

- `createRouter()` from `utils/routes/router.ts` — never `new Hono()`. It gives `c.get('config' | 'db' | 'logger' | 'requestId')` types.
- Request contracts are zod schemas in `packages/shared/src/` (`@rocketpod/shared/<module>`; UI and CLI import them too). Validate with `validate('json' | 'query' | 'param', schema)` from `utils/routes/validate.ts`; a bad input becomes the shared 400 envelope with `code: 'validation_failed'`.
- Read config via `c.get('config')`, never `c.env`. Platform capabilities are passed INTO services from the route, never read inside them: `c.get('platform').jobs` → `createInvitation(db, cfg, logger, jobs, …)`, `c.get('platform').storage` → the `StorageService`; the realtime hub only ever via the `realtime` that `withAuth` returns.
- Body limits: the global `jsonBodyLimit` (1 MB) skips the `UPLOAD_PATHS` (`/api/files`, `/api/ai/documents/upload`; `isUploadPath`); each mounts `uploadBodyLimit` (`MAX_UPLOAD_BYTES + 64 KB`) on its `POST` — `files.ts` enforces the exact 5 MB per file (413 `payload_too_large`) and the avatar allowlist (415 `unsupported_media_type`) itself. A new upload route must do the same two things — the transport cap is not the per-file limit.
- Throw typed errors from `utils/core/errors.ts` (`NotFoundError`, `ForbiddenError`, ...). Do not hand-roll `c.json({ error }, 4xx)`; `middleware/error-handler.ts` owns the envelope `{ error, statusCode, code?, details? }`.
- Success bodies are bare domain objects (no envelope). Lists use `paginatedResponse(item)` from `@rocketpod/shared/pagination` → `{ items, pagination: { page, pageSize, total, totalPages } }`.
- Auth is applied AT THE MOUNT in `index.ts` (`app.use('/api/x/*', authMiddleware); app.route('/api/x', xRouter)`), never inside a route file. Every tenant-scoped query carries `eq(table.tenantId, tenantId)` from the auth context — never from the body/query.
- Side effects that may outlive the response (activity writes, realtime nudges, the tracer flush) go through `defer(...)` from `withAuth` (= `c.executionCtx.waitUntil`, backed on Node by the server's tracked defer set; awaited inline when there is no ExecutionContext); a detached promise is killed when the response ends. **Inside a stream there is no `defer`**: the request's `db` is closing in the deferred work once the Response is returned, so open `streamDatabase(c)` (`utils/routes/route-helpers.ts`), await every write and `tracer.flush()`, and `close()` it in `finally` (full stream rules: `../services/ai/CLAUDE.md`).
- Routes enqueue, never run: anything longer than a request is a pg-boss job or a durable run. Transactional emails are `email.send` jobs (`enqueueJob(c.get('platform').jobs, …)` inside the service) — except the magic link, which stays inline because a person is waiting on it.
- Realtime: services `nudge(realtime, realtimeEvent('member.changed', tenantId, { id }))`; the route only passes `realtime` through. Emit after the transaction commits.
- **A sign-in path asks the SSO policy before it admits anyone** (`ServerPlugin.ssoPolicy`): `ssoDecisionFor(db, cfg, emails, logger)` (`auth/sso.ts`, the barrel bound into the pure `evaluateSsoPolicyForAll`) then `ssoAllows(decision, 'core' | { pluginId, connectionId? })`; a refusal is `ssoRequiredRedirect(c, decision, { returnUrl })`, or 403 `sso_required` + `details.method` for a JSON route. Pass every address the sign-in involves (asserted and account). A NEW sign-in path that skips it is a hole in every customer's SSO requirement. Never import `routes/auth/sso` from `plugins/api/**` statically — it reads the barrel (`identity.ts` uses `await import`).
- AI permissions: `AiConfig`/`Prompt`/`Document` admin+ `manage`, member `read` (+ `create Document`); `Conversation`/`AgentRun` `manage` for all with ownership route-side (`userId` filter → 404; `isAdminLevel(auth)` widens runs), and answering an interrupt is `update AgentRun` plus the agent's `approvers`; `Trace` is `read` for owner/admin/support only — a span holds other people's prompts, so members get nothing, not even their own runs; `Feedback` is `create` for every member (on an answer they can read — the service checks, a foreign id is 404) and `read` for admin+ only.

## CLI login (`auth/cli.ts`)

`GET /auth/cli?redirect_uri=http://127.0.0.1:<port>/callback&hostname=<machine>`. `redirect_uri`
must be exactly `http://127.0.0.1:<port>/callback` or `http://localhost:<port>/callback` (any port,
`http:` only, no query/hash/userinfo — `validateCliRedirectUri`), else 400 `invalid_redirect_uri`;
that allowlist is what makes handing a key over in a query string acceptable. No session → 302
`/login?returnUrl=<this url>`; session without a tenant → 302 `/select-tenant?returnUrl=` (skipped in
`TENANCY_MODE=single`); otherwise 302 `/cli/confirm` (the SPA page). The GET creates nothing.
`POST /auth/cli/confirm` (`cliConfirmRequestSchema`, cookie session, so the CSRF middleware applies)
re-validates the target, then `mintApiKey` (the same helper `POST /api/keys` uses) creates a tenant
key named `cli:<sanitised hostname>` with scopes `['*']`, records `api_key.created` (`via: 'cli'`)
in `waitUntil`, and answers `{ redirectTo: 'redirect_uri?key=&tenant_id=&tenant_name=&state=' }`
for the page to navigate to (`form-action 'self'` rules out a native form redirecting to loopback).
`state` is the CLI's own value, passed through. The plaintext is never logged and is shown once;
the CLI stores it. The server never redirects with `?error=` — failures
surface as the JSON envelope on this route.

## Route anatomy

```ts
router.post('/', validate('json', createThingSchema), async c => {
  const { db, tenantId, user, defer } = withAuthAndDb(c) // throws 401 / 403 no_tenant|pending_approval
  guardPermission(c, 'create', 'Thing')
  const [row] = await db.insert(things).values({ ...c.req.valid('json'), tenantId }).returning()
  defer(() => recordActivity(db, { tenantId, userId: user.id, type: 'thing.created', subjectType: 'Thing', subjectId: row.id }))
  return c.json(row, 201)
})
```

`withAuth(c)` is the tenant-free variant (`tenantId: string | null`) for invite accept, pending
invitations, access requests and `/api/admin/*`. Both also return `cfg`, `logger`, `defer` (runs a side
effect through `waitUntil` and logs instead of throwing), `realtime`
(`{ defer, hub }` — hand it to a service that nudges) and `tracer` (the request's span
recorder, or `noopTracer` when no sink exists, for `withAgentTrace` / `traceChatClient`). `requireMultiTenant(cfg)` → 404
`tenancy_mode_single`. `uuidParam(c, 'id')` → 404 for a non-UUID `:id` (never a DB error).
`streamDatabase(c)` → a second `{ db, close }` for the body of an SSE stream.

New endpoint checklist: schema in `packages/shared/src/` → `validate(...)` → auth seam + permission
guard → tenant-scoped query → tests in `tests/api/` → update this file if a new router appears.
