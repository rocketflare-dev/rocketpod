# Row-level security — posture and rollout

**Runtime isolation is predicates-only by default (`TENANT_SCOPE_MODE=off`).** Every domain query
carries `eq(table.tenantId, tenantId)` from the auth context, and that never changes. Postgres RLS
ships as *inert scaffolding*: policies exist on every tenant table, the app role exists but cannot
log in, and turning enforcement on is a configuration change gated by the spike below (D1).

Why not on by default: the proven RLS pattern (a session GUC on a pinned connection) assumes a
connection owned by one request. The Node server holds one pooled postgres.js client per process
(D41), and a deployment may also put PgBouncer in transaction mode in front of Postgres — both hand
a connection to another request between transactions — so the GUC must be set *inside a
transaction* per request (`set_config(…, true)`, transaction-local). Nobody flips this without
measuring it first.

## What ships inert

| Piece | Where | Effect while `off` |
|---|---|---|
| `tenantIsolation('<table>')` on every table with `tenantId`; `membershipIsolation()` on `users` | `apps/web/src/db/schema/rls.ts`, each schema file | policies generated by drizzle-kit, `FOR ALL TO rocketpod_app`, `USING` + `WITH CHECK` on `tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid`. Owner role bypasses them |
| `RLS_EXCLUDED_TABLES` / `RLS_REVOKED_TABLES` with reasons | `apps/web/src/db/schema/rls.ts` | the allow-list for tables without a tenant column (and platform tables such as `rate_limits`, `operation_locks`, revoked from the app role) |
| `apps/web/tests/api/rls-coverage.test.ts` | catalog-driven | fails CI if a tenant table lacks a policy or an untenanted table lacks an exclusion; the `pgboss` and `openworkflow` schemas are outside it |
| `apps/web/scripts/db-roles.ts --phase=role\|grants` | wrapped by `pnpm db:migrate` / `node dist/migrate.js` | creates `rocketpod_app` via SQL — `NOLOGIN`, `NOSUPERUSER`, `NOBYPASSRLS` (set explicitly only when the owner is a superuser, verified after on every host); grants DML; REVOKEs auth-infrastructure tables |
| `withTenantScope(db, tenantId, fn)` | `apps/web/src/db/tenant-scope.ts` | `off` → `fn(db)`. `enforce` → `db.transaction(tx => set_config('app.tenant_id', $1, true); fn(tx))` on an app-role client — not wired yet: the app-role pool would come from `APP_DATABASE_URL` |
| `apps/web/tests/api/rls.test.ts` | skipped unless `enforce` | the enforcement properties (zero rows on a missing predicate, `42501` on a cross-tenant write) |

Threat model, stated honestly: RLS defends against a **forgotten predicate**, not SQL injection —
the app role can call `set_config` itself.

## The spike (half a day; run before anyone sets `enforce`)

Against the Postgres the deployment uses, through the same pooling path production will have (the
process pool directly, or PgBouncer in transaction mode if you run one), with the app role
(`APP_DATABASE_URL`) given a password by `db-roles.ts`. From a deployed preview or a local
`node dist/server.js` against that database:

1. **Correctness** — 200 concurrent requests alternating tenants A/B through the transactional
   `set_config(..., true)` path. Zero cross-tenant rows; a predicate-less `select count(*)` inside
   the transaction returns only the tenant's rows; a query *outside* any transaction on the app
   pool returns zero rows (fail-closed proof).
2. **Pooler leak** (PgBouncer only) — tenant A runs `select * from <table>` (no predicate) in its
   transaction, then tenant B runs the identical statement on the same pooler. If B ever sees A's
   rows, the pooler is not resetting transaction-local state and must not front the app role.
3. **Latency** — p50/p95 of `BEGIN + set_config + one select + COMMIT` vs a bare select; try a
   simple-protocol `BEGIN; select set_config(...)` pipeline with a regex-validated UUID to save a
   round trip.
4. **Role plumbing** — `db-roles.ts --phase=role` → `migrate` → `--phase=grants` against the
   database as its owner (on a managed service, the account it gives you); `ALTER DEFAULT
   PRIVILEGES` and `REVOKE` succeed; `pg_roles` shows `rolbypassrls = false` for `rocketpod_app`;
   the owner still bypasses policies without `FORCE`.
5. **Pool behaviour** — hold the transaction open 2 s in 50 concurrent requests; watch the pool's
   wait time (`DATABASE_POOL_MAX`) and the server's connection count and error rate (validates the
   documented warning about long transactions).

**Go/no-go.** Go if 1 passes, 2 passes (or no pooler is used), and 3 costs under ~10 ms p95. Then
`enforce` is promoted to "supported" here and this doc gains the numbers. No-go: this section is
rewritten as "not supported over <that pooling path>; a direct connection for the app role is the
alternative". Record the outcome and date below.

## Turning `enforce` on (only after a Go)

1. Wire the app-role connection into `withTenantScope`'s caller (the kit reads none today): a second
   process pool opened from `APP_DATABASE_URL` (the app role's URL — direct, or through a
   transaction-mode pooler that passed step 2).
2. Set `APP_DATABASE_URL` for `apps/web/scripts/db-roles.ts` in the migration environment too — the
   compose `migrate` service, the chart's migrate hook (`secrets.APP_DATABASE_URL` or your
   `existingSecret`), and `apps/web/.env` locally. The username must equal `APP_ROLE` in `rls.ts`;
   the script reconciles the role's password to the URL, so credential and grant cannot drift.
   Run the migration (roles → migrate → grants) once against each database.
3. Flip `TENANT_SCOPE_MODE=enforce` in the deployment's config (the chart's `config`, or the compose
   `.env`) — staging first, soak, then production.
4. Watch: error rate, `42501` count, p95 latency, connection counts. **A 404 for a row the user
   should see is the signature failure** — a genuinely cross-tenant read is missing its escape hatch
   (`apps/web/tests/config/unscoped-allowlist.test.ts` pins the allowed ones).

## Rollback

`TENANT_SCOPE_MODE=off` and redeploy. There is no migration to reverse; the policies stay in place
and are simply not enforced for the owner role.
